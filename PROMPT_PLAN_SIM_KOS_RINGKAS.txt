Buat PRD, spesifikasi teknis, dan rencana implementasi Tugas Akhir Praktikum Sistem Informasi untuk Sistem Informasi Manajemen Kos (SIM Kos). Implementasi akan dibantu AI coding agent di Google Antigravity. Gunakan bahasa Indonesia, susun task konkret yang dapat dieksekusi dan diuji bertahap. Sekarang buat rencana, bukan kode aplikasi. Targetnya aplikasi web dengan database nyata yang dapat didemonstrasikan lokal di laptop Windows dan dipahami mahasiswa.

1. KONTEKS DAN SUMBER

Proyek melanjutkan laporan yang sudah dikerjakan: Modul 1 Project Charter, Modul 2 Analisis Proses Bisnis/BPMN, Modul 3 Analisis Kebutuhan Informasi/IRM, serta dokumen ketentuan TA. Ringkasan berikut cukup digunakan tanpa lampiran. Jangan mengaku membaca dokumen yang tidak tersedia.

Bedakan persyaratan TA, kebutuhan laporan, keputusan teknologi, dan asumsi implementasi. Contoh Sistem Informasi Toko dalam ketentuan hanya ilustrasi; studi kasus tetap kos. Pertahankan tiga proses bisnis dan tambahkan kewajiban TA yang belum dijelaskan dalam modul, seperti audit trail.

Sistem melayani satu usaha kos. Masalah: status kamar tidak akurat, pembayaran sulit diperiksa, data penghuni tersebar, keluhan/perbaikan sulit dipantau, dan pendapatan sulit direkap. Tujuan: mengintegrasikan kamar, penghuni, penempatan, tarif, pembayaran, fasilitas, keluhan, serta laporan untuk mendukung keputusan. Jelaskan hubungan Data → Proses → Penyimpanan → Informasi → Keputusan.

Di luar ruang lingkup laporan: kos milik pihak lain, jual beli properti, keuangan pribadi, penggajian, layanan eksternal, dan pembayaran kebutuhan pribadi. Untuk menyederhanakan implementasi, jangan menambahkan marketplace, multi-tenant SaaS, aplikasi mobile native, payment gateway, WhatsApp API, atau chatbot AI. AI digunakan untuk membangun aplikasi.

2. TEKNOLOGI YANG DIPILIH

Gunakan Laravel (PHP), arsitektur monolit, Blade, MySQL, Bootstrap 5, dan Chart.js. Gunakan autentikasi session, middleware/policy untuk otorisasi, migration, seeder, serta transaksi database. Gunakan halaman cetak dengan Save as PDF untuk laporan dan bukti pembayaran. Simpan aset frontend lokal agar demo tidak bergantung internet setelah instalasi.

Versi PHP, Laravel, dan dependency harus diperiksa kompatibilitasnya sebelum instalasi. Sertakan setup Windows, pengujian, Git/GitHub, serta ekspor/impor database .sql. Hosting tidak wajib. Stack ini keputusan proyek, bukan ketentuan dosen.

3. ROLE DAN AKSES

- Admin/Pengelola: mengelola master data, akun, penempatan, tarif, pembayaran, fasilitas, keluhan, tindak lanjut, dan informasi operasional.
- Pemilik: memantau kamar, penghuni, pembayaran, pendapatan, fasilitas, keluhan, dashboard, laporan, dan audit trail. Akses read-only menjadi asumsi awal.
- Penghuni: melihat kamar/penempatan, kewajiban dan riwayat pembayaran sendiri; menyampaikan serta memantau keluhan sendiri.

Buat matriks permission per modul/aksi. Terapkan pembatasan di server dan kepemilikan data, bukan hanya menyembunyikan menu. Akun dibuat admin sebagai asumsi awal; tetapkan batas pengelolaan akun/role agar tidak terjadi eskalasi akses.

4. KETENTUAN WAJIB TA DAN PENERAPANNYA

A. Login/logout dengan username atau email dan password; minimal dua role. Proyek menggunakan tiga role di atas.

B. Minimal tiga master: Kamar, Penghuni, Fasilitas. Masing-masing memiliki tambah, tampilkan, edit, hapus, cari, detail, validasi. Tentukan field, tipe, relasi, aturan wajib/unik, dan pesan error. Hapus data uji yang belum direferensikan harus dapat didemonstrasikan. Batasi penghapusan atau arsipkan data terkait transaksi agar histori tidak hilang.

C. Minimal satu transaksi utama lintas tabel: Pembayaran Sewa. Tetap implementasikan Penempatan dan Keluhan sesuai laporan. Rancang nomor pembayaran otomatis unik, validasi, penyimpanan, perubahan status, serta bukti cetak.

D. Dashboard minimal tiga KPI, dua grafik, satu tabel; seluruhnya dihitung dari database dan berubah setelah transaksi. Gunakan empat KPI: kamar kosong, kamar terisi, pendapatan periode terpilih, jumlah kewajiban belum dibayar. Grafik: tren pendapatan bulanan dan distribusi status kamar saat ini. Tabel: kewajiban belum dibayar atau pembayaran terbaru. Definisikan rumus, filter, sumber data, kondisi kosong, dan keputusan yang didukung. Status kamar saat ini bukan histori okupansi. Penghuni hanya melihat informasi pribadi.

E. Minimal dua laporan: Pembayaran/Pendapatan dan Status Pembayaran per Periode. Setiap laporan memiliki filter tanggal/periode, pencarian, pengurutan, total/rekapitulasi, dan cetak. Bedakan tanggal pembayaran dengan periode sewa. Nyatakan apakah status merupakan kondisi terkini untuk periode terpilih; jangan mengklaim histori pada tanggal tertentu tanpa data pendukung.

F. Audit trail minimal menyimpan nama pengguna, aktivitas, modul, data yang diproses, waktu. Catat perubahan master, penempatan, pembayaran, keluhan, dan akses/cetak laporan. Pengguna biasa tidak dapat mengubah log. Jangan menyimpan password/token. Pertahankan identitas pelaku ketika akun diarsipkan.

G. Database nyata dengan PK, FK, relasi, tipe data sesuai, serta data contoh. Jangan memakai localStorage atau array statis sebagai penyimpanan utama.

H. UI rapi, konsisten, navigasi jelas, responsif di laptop, validasi form, notifikasi berhasil/gagal, kondisi kosong/loading/error, dan konfirmasi hapus. Bahasa Indonesia, Rupiah, zona waktu Asia/Jakarta.

5. PROSES BISNIS MODUL 2

Penempatan: admin memeriksa penghuni dan ketersediaan kamar → keputusan “Kamar Tersedia?” → jika ya, mencatat penempatan, memperbarui status penempatan/kamar menjadi terisi, menampilkan hasil. Jika tidak, proses ditunda tanpa membuat penempatan aktif.

Pembayaran: penghuni membayar → admin memeriksa jumlah, tarif, periode → keputusan “Pembayaran Sesuai?” → jika ya, mencatat dan memperbarui status/riwayat; jika tidak, memberi informasi ketidaksesuaian untuk penyesuaian/pembayaran ulang. Pembayaran tidak sesuai tidak dianggap lunas atau pendapatan sah. Pembayaran berlangsung di luar aplikasi dan dicatat admin; gateway/unggah bukti tidak wajib.

Keluhan: penghuni menyampaikan keluhan kamar/fasilitas → admin mencatat/memeriksa → keputusan “Perlu Tindak Lanjut?” → jika ya, menangani dan memperbarui status; jika tidak, menutup tanpa tindak lanjut. Simpan tindakan, tanggal, status, alasan penutupan. Penghuni melihat perkembangan sendiri.

Ambiguitas sumber: narasi menempatkan penutupan keluhan pada admin, tetapi kotak diagram berada pada lane penghuni. Tandai untuk klarifikasi; sementara usulkan admin mengikuti narasi.

6. KEBUTUHAN INFORMASI MODUL 3

Petakan setiap IRM ke halaman, field, tabel, permission, dan acceptance criteria:
IRM-01 Admin: identitas penghuni sebelum memilih kamar; nama, telepon, tanggal mulai tinggal.
IRM-02 Admin: kamar kosong sebelum penempatan; nomor/status kamar.
IRM-03 Admin: kamar tersedia saat memilih; kamar dan penghuni.
IRM-04 Admin: hasil penempatan; penghuni, kamar, tanggal mulai, status.
IRM-05 Admin: kewajiban saat memeriksa pembayaran; tarif, periode, penghuni.
IRM-06 Admin: kesesuaian setelah menerima pembayaran; jumlah, tarif, periode.
IRM-07 Admin: status setelah pembayaran sesuai; penghuni, periode, jumlah, status.
IRM-08 Penghuni: riwayat sendiri setelah dicatat; periode, tanggal, jumlah, status.
IRM-09 Admin: detail keluhan setelah diterima; penghuni, isi, kamar, fasilitas, tanggal.
IRM-10 Admin: dasar tindak lanjut setelah pemeriksaan; isi keluhan, fasilitas, kondisinya.
IRM-11 Admin: perkembangan setelah penanganan; keluhan, tindakan, tanggal, status.
IRM-12 Penghuni: perkembangan keluhan sendiri setelah diperbarui; tindakan dan status.

Pemilik tetap memiliki akses pemantauan berdasarkan Modul 1. Informasi harus relevan, akurat, lengkap, dan tepat waktu.

7. ASUMSI DAN INTEGRITAS DATA

Kapasitas kamar, jatuh tempo, cicilan, prorata, dan skema tagihan belum ditetapkan laporan. Nyatakan baseline berikut sebagai asumsi:
- Satu penghuni aktif per kamar dan satu penempatan aktif per penghuni.
- Sewa bulanan dibayar penuh; tanpa cicilan, denda otomatis, deposit, prorata.
- Representasikan kewajiban/tagihan per penempatan dan periode agar penghuni tanpa pembayaran tetap tercatat belum bayar. Ini elaborasi teknis, bukan proses baru yang diklaim dari BPMN.
- Putuskan aturan periode pertama/terakhir, jatuh tempo, dan pembuatan tagihan. Proses manual admin yang idempoten boleh digunakan tanpa scheduler.
- Simpan snapshot tarif per kewajiban agar perubahan tarif tidak mengubah histori.
- Cegah tagihan, pembayaran sah, nomor transaksi, dan penempatan ganda, termasuk request bersamaan. Gunakan transaksi database serta constraint/locking sesuai kebutuhan.
- Bedakan status kewajiban belum bayar/lunas dari pemeriksaan pembayaran sesuai/tidak sesuai.
- Tentukan mekanisme koreksi/pembatalan yang menjaga histori; jika ditunda, larang perubahan bebas transaksi sah.
- Atur penghentian penempatan agar kamar tersedia kembali tanpa menghapus histori; tandai sebagai elaborasi siklus penempatan.
- Fasilitas dapat berada di kamar atau area bersama. Gunakan nominal uang berpresisi tepat, bukan floating point.

8. KELUARAN RENCANA

Susun bagian berikut sebagai dokumen Markdown atau format ekuivalen platform:

A. PRD: masalah, tujuan, scope, user stories, kebutuhan fungsional/nonfungsional, role, asumsi. Semua kewajiban TA serta fasilitas/keluhan merupakan fitur inti.

B. Matriks kebutuhan: setiap syarat TA dan IRM-01–12 → fitur/halaman → data → test case → bukti demo.

C. Arsitektur/database: struktur folder, alur request, keamanan, ERD/kardinalitas, data dictionary, PK/FK, nullability, unique/index, aturan hapus, state transition, transaksi, seed. Evaluasi entitas role, user, kamar, penghuni, penempatan, fasilitas, tagihan, pembayaran, keluhan, tindak lanjut, activity log. Jelaskan kebutuhan tabel tarif terpisah.

D. Spesifikasi fitur: aktor, permission, halaman/field, validasi, alur sukses/gagal, perubahan data, audit, acceptance criteria, perhitungan dashboard/laporan. Pertahankan tiga alur BPMN; diagram Mermaid boleh menjadi pendamping, bukan diklaim BPMN standar.

E. Task implementasi: setup → database/seed → autentikasi/otorisasi → master → penempatan/tagihan → pembayaran → keluhan → dashboard/laporan → pengujian → dokumentasi. Integrasikan audit sejak awal. Setiap task memiliki ID, tujuan, dependensi, cakupan, perkiraan file/modul, langkah, acceptance criteria terukur, verifikasi, definition of done. Pecah menjadi pekerjaan kecil yang utuh.

F. Prompt Antigravity: prompt pembuka dan per milestone berisi konteks, dokumen rujukan, tujuan, batas perubahan, acceptance criteria, tes, keluaran. Minta agent membaca codebase/environment, membuat implementation plan, mengimplementasikan, menguji, dan melaporkan walkthrough. Sertakan catatan progres untuk pergantian sesi. Jangan menganggap integrasi otomatis dengan situs perencana. Jangan mengarang hasil tes/screenshot.

G. Test plan: ID, prasyarat, data, langkah, expected result; actual result/status kosong sebelum diuji. Cakup login salah, akses role/data penghuni lain, CRUD tiga master, validasi, kamar tidak tersedia, penempatan bersamaan, pembayaran salah/duplikat, tagihan belum bayar, perubahan tarif, keluhan ditangani/ditutup, filter/total laporan, perubahan KPI, audit, persistensi setelah restart. Utamakan tes integrasi transaksi/otorisasi dan uji UI alur utama.

H. Demo/pengumpulan: source code, database .sql teruji impor, link GitHub, dokumentasi masalah/tujuan, proses bisnis, kebutuhan pengguna, ERD, role, master, transaksi, dashboard/laporan, audit, test case. Tambahkan README Windows, akun demo setiap role, data sintetis beberapa periode, backup/restore, reset demo aman. Screenshot dari aplikasi nyata setelah implementasi.

Urutan demo: masalah/tujuan → proses bisnis → role → login berbeda → tambah/edit/cari/hapus master → transaksi selesai → perubahan data → dashboard → laporan periode → audit. Sertakan input dan hasil yang diharapkan.

I. Pembelajaran/tim: usulkan pembagian seimbang maksimal dua mahasiswa dan saling review. Keduanya memahami keseluruhan sistem. Sertakan penjelasan alur transaksi/relasi/perhitungan serta latihan tanya jawab presentasi. Estimasi milestone adalah asumsi; deadline belum diberikan.

Mulai dengan ringkasan dan keputusan/asumsi. Untuk detail yang belum ada, pilih default sederhana dan jelaskan. Ajukan maksimal lima pertanyaan penting bila diperlukan sambil tetap menyusun draft. Jangan mengarang aturan kampus atau persetujuan dosen. Akhiri dengan pemeriksaan cakupan seluruh ketentuan TA, tiga proses, dan 12 IRM. Hasil harus konkret, konsisten, siap dieksekusi AI, dan mudah dijelaskan mahasiswa.
